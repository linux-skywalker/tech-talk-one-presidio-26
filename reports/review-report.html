GPU on Kubernetes: project review

Proof of concept for "Beyond kubectl apply: Elevating GPU Workflows with NVIDIA on Kubernetes" · RTX 4070 (12 GB), native Ubuntu 24.04, driver 590.48.01, k3s, NVIDIA GPU Operator v26.7.2 · generated 2026-10-22

Thesis. Kubernetes with NVIDIA's tools makes GPU work easier to run than doing it by hand. The same model (Qwen2.5-1.5B-Instruct, LoRA fine-tune on 800 examples, served with vLLM) was done both ways. All numbers are single runs on this one machine.
28 skilled training job (force-deleted pod) is training again, no person involved (manual: stays dead)
77 to 81 skilled server is answering again on Kubernetes, no person involved
38% to 93%GPU busy: one tiny model alone vs six models sharing the card (same traffic per model)
Samespeed and GPU use as the manual way: 90.5% vs 89.1% busy, 1774 vs 1773 tok/s

GPU busy is NVIDIA DCGM's utilization: the share of time at least one kernel was running. It reaches 93% with six models at moderate traffic. It is not a measure of useful work: at saturation one copy alone already delivers the same total requests per second (40.5 vs 41.9), so sharing does not add throughput there. What sharing adds is room for several different models on one card.

Heavy load: six copies delivered about 5x less total throughput than one copy (2474 vs 12814 tok/s), because one tiny server already fills the card. Sharing helps when many models each get light traffic.

6. Honest limits

  • Single runs on one machine. Recovery times come from pod logs and polling, about plus or minus 3 s.
  • Kubernetes was not faster and did not raise GPU utilization by itself. The gain is unattended recovery, sharing and visibility.
  • First-time setup was about twice as long on Kubernetes (image builds).
  • The GPU Operator did not install the driver or the container toolkit here (both were turned off). Turning its toolkit installer on broke the node.
  • Not tested: Growing (more nodes), Moving to another cloud, MIG, crash isolation between shared workloads.
